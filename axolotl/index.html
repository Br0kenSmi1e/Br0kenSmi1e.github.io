Axolotl

November 2026 · A proof checker that never grows up

The axolotl is a salamander that never grows up. It stays in its larval form for its whole life — gills out, fully functional, breeding happily as a perpetual juvenile. I named my theorem prover after it, because that is the design philosophy: a proof checker that stays small on purpose.

Every serious proof assistant — Lean, Coq, Agda — rests on a kernel, a small core of code that actually decides whether a proof is valid. Everything else is ergonomics. The folklore says a kernel can be tiny, and I wanted to know how tiny. Axolotl is my answer: about 250 lines of Rust for the kernel, another 130 for a frontend, zero dependencies. And it checks real proofs — including a proof that 2 + 2 = 4.

Terms are six lines

The entire language of axolotl fits in one enum:

pub enum Term {
    Var(usize),              // de Bruijn index
    Lambda(TermRef),         // anonymous binder
    Apply(TermRef, TermRef),
    Pi(TermRef, TermRef),    // dependent function type
    Type(usize),             // universe at a level
    Ann(TermRef, TermRef),   // type annotation
}

Variables are de Bruijn indices: Var(0) is the nearest enclosing binder, Var(1) the next one out. No names, no capture, no α-renaming — substitution bugs in name-based systems are a genre of suffering that simply doesn't exist here. Everything is an Rc, so subterms are shared and cloned by pointer bump.

This is the full calculus: the lambda calculus plus dependent function types and a hierarchy of universes. Dependent types buy you the Curry–Howard correspondence for free — a Pi type is a universal statement, a lambda is a proof of it.

Evaluation without substitution

A proof checker constantly has to answer: are these two types the same? And "the same" means the same up to computation — 2 + 2 and 4 must be recognized as equal. The classic approach is substitution-based reduction; the modern one, which axolotl uses, is normalization by evaluation (NbE).

The idea is to never substitute into syntax at all. Instead, terms evaluate into a separate world of values, where lambdas become closures capturing their environment:

pub enum Value {
    VLambda(Closure),
    VPi(ValueRef, Closure),
    VType(usize),
    VNeutral(usize, Vec<ValueRef>),  // a stuck variable, plus its arguments
}

Evaluation is then almost insultingly small:

pub fn eval(env: &Env, term: &TermRef) -> ValueRef {
    match term.as_ref() {
        Term::Var(i) => env[env.len() - 1 - *i].clone(),
        Term::Lambda(body) => vlambda(capture(env, body)),
        Term::Apply(func, arg) => vapply(&eval(env, func), eval(env, arg)),
        Term::Pi(dom, cod) => vpi(eval(env, dom), capture(env, cod)),
        Term::Type(level) => vtype(*level),
        Term::Ann(term, _) => eval(env, term),
    }
}

Two details worth pausing on. First, a neutral is a computation stuck on a free variable — a variable applied to some arguments that can't reduce further. Neutrals are what make open terms computable: under a binder, a variable isn't a value yet, so application just accumulates a spine of arguments. Second, Ann evaporates during evaluation. Annotations exist for the type checker, not the machine.

To compare values, or to print a normal form, you read back a value into a term, generating fresh variables as you go under binders. Terms count binders inward (indices); values count outward (levels). The dance between the two — depth - 1 - level in one direction, len - 1 - index in the other — is the fiddliest part of the whole codebase, and the entire price of avoiding names.

Type checking in two directions

Axolotl's checker is bidirectional, which is a fancy name for a simple discipline: some terms produce a type (infer), and some terms can only be verified against one (check). The one rule that shapes everything is that a bare lambda cannot be inferred — a function out of thin air doesn't know its own domain. Hence the Ann node: you annotate a lambda once, and from then on the checker can propagate.

Checking a lambda against a Pi is where the NbE machinery pays off. You don't substitute the argument type into the codomain; you apply the codomain's closure to a fresh neutral variable and recurse:

(Term::Lambda(body), Value::VPi(domain, codomain)) => {
    let fresh_var = fresh(env.len());
    let body_ty = capply(codomain, fresh_var.clone());
    check(&extend(&ctx, domain.clone()), &extend(&env, fresh_var),
          body, &body_ty)
}

The fallback case of check is where computation meets logic: infer a type, then ask whether the inferred type and the expected type are convertible — equal up to evaluation. Conversion checking is a structural walk over values, applying closures to fresh variables to peek under binders, with one cheap shortcut: if two values are the same Rc pointer, they're equal. Conversion is where 2 + 2 = 4 stops being an opinion and becomes a fact the kernel can certify.

The frontend: names, and a knob for opacity

Nobody wants to write de Bruijn indices by hand (well — my test suite does, and I no longer recommend it). The frontend has a surface syntax with named binders, and a resolve pass that compiles names to indices by walking a scope. Two of my favorite tests in the project are nothing more than traps for the classic bugs of this pass: an inner binder shadowing an outer one, and a Pi domain being resolved before its own binder enters scope.

The frontend also has the project's most opinionated design: three kinds of top-level declaration, which differ in what the rest of the world is allowed to see.

  • An axiom declares a name and a type. It enters the environment as a bare neutral — permanently opaque, never reduces.
  • A definition is checked against its stated type, then enters the environment as its evaluated value — fully transparent, unfolds on demand.
  • A theorem is like a definition whose proof is checked and then thrown away: it enters as an opaque neutral. Proof irrelevance by construction — once certified, a proof's only job is to exist.

One drive loop threads a scope, a typing context, and an environment through the declarations in lockstep, and the end-to-end test asserts the opacity contract directly: the axiom and the theorem sit in the environment as empty-spined neutrals, while the definition has visibly computed itself into an application of succ to zero.

The payoff: 2 + 2 = 4, certified

The test suite is where the tiny kernel starts to feel like magic. There are no inductive types, so numbers are Church numerals — a natural number is its own iterator. And equality is the Leibniz definition: two things are equal when every property of one is a property of the other. Both fit in a few lines of raw terms, and both just work, because the kernel doesn't know or care that they are encodings.

Transitivity of equality is the first test, and its proof is a one-liner: given proofs of x = y and y = z, apply the second to the property Eq x · z, then apply the first to the result. Eight nested lambdas of de Bruijn arithmetic — unreadable, and certified:

assert_eq!(certify(&statement, &proof), Ok(()));

And the trophy test: state that plus 2 2 = 4 of Church naturals, prove it with a single reflexivity constant, and let certify do the rest. Reflexivity only proves t = t — so the only reason the certificate is accepted is that conversion checking genuinely evaluates plus 2 2 down to 4 inside the kernel. The arithmetic is performed by the type checker, during conversion, as a side effect of asking whether two types are equal. That's the whole Curry–Howard miracle in one assert_eq!(…, Ok(())).

What it can't do

In the spirit of the animal: the missing features are the point, but let me name them. There is no parser yet — the Parser trait is a stub, and programs are built as Rust trees. There are no inductive types, no termination checking (so it's a consistent logic only if you don't loop the checker itself — an axolotl trusts you), and no implicit arguments or unification. Axiom means what it says: postulate anything and the kernel will believe you. Universes are a strict hierarchy with no cumulativity.

But everything it does do, it does in code you can read in one sitting, and the trust base is genuinely those 250 lines. That's what I wanted from the project: not a tool, but a demonstration that the gap between "the lambda calculus" and "a machine that certifies 2 + 2 = 4" is an afternoon of careful Rust — plus a lifetime supply of de Bruijn off-by-one errors, which the tests now remember so I don't have to.
