Why a Program Can Check a Proof

November 2026

I recently built axolotl, a proof checker in about 600 lines of dependency-free Rust. But this post is not about the code. It's about the question the code answers — the question I actually wanted to understand by building it:

Why can a program check a proof at all?

I came to this question with a prior, and the prior was wrong in an instructive way. My model of theorem proving was: pattern matching plus rewriting on syntax trees. This post is the story of exactly where that model breaks — provably, not philosophically — and of the twist at the end, where the broken model turns out to be right after all, one level down. That twist is the reason proof checkers can exist.

The obvious guess: proving is rewriting

First, a precise definition, because everything hinges on it:

Rewrite step: you have an equation you already know — a definition or a previously proven lemma — and you replace a piece of your formula with an equal piece.

Under this definition, some proofs really are pure rewriting. Expanding (a + b)² = a² + 2ab + b² means: distribute, collect, done — every step replaces a subexpression by an equal one, justified by an algebra law you already had. And this isn't just loosely true of algebra: Birkhoff's completeness theorem says an equation is provable in equational logic if and only if it's derivable by substituting equals for equals. For pure equations, a proof literally is a rewrite sequence.

So the guess is not naive. It's a theorem — about a small fragment of logic. The question is what happens outside that fragment.

Stuck at step zero

Prove: for every natural number n, n + 0 = n. Your entire toolbox is the definition of addition:

(rule 1)  0 + m       =  m
(rule 2)  succ(k) + m =  succ(k + m)

Now try to rewrite the goal n + 0 = n, where n is an arbitrary variable. Rule 1 matches 0 + m — zero on the left; our zero is on the right. Rule 2 matches succ(k) + m — but our left argument is a bare variable, not a successor. There is not a single legal rewrite. Not "hard to find" — none exists. A pure rewriting system is stuck at step zero on one of the first theorems of arithmetic.

Yet the theorem is provable — by induction, a move that is not a rewrite. Induction says: prove it for zero, then prove that if it holds for k, then it holds for succ(k). Look closely at the "if" part: the logic hands you a brand-new equation, k + 0 = k, out of nowhere. No equation you had contains it; no rewrite produced it. It is a fresh assumption, manufactured by a rule of the logic. Only then does rewriting finish the job: succ(k) + 0 → succ(k + 0) → succ(k), the last step spending the gift.

Other moves break the rewrite model even earlier, because there is nothing to rewrite at all. Prove "if P, then (if Q, then P)": the formula contains no equals sign, no subexpressions to simplify. The proof is "suppose P; suppose Q; done — P is what I had." The move suppose doesn't transform the formula; it changes the rules of the game mid-play, adding a usable fact to your toolbox and discharging it later. Same story for witnesses (to prove "there exists x such that P(x)", you must produce a term — nothing in the goal's syntax tells you which) and for case splits (the proof forks into branches).

Even the heartland of the rewriting intuition fights back: orient x + y = y + x either way and it loops forever, a + b → b + a → a + b → …. Making rewriting work at all on equations requires an ordering that forces every step downhill — the idea at the core of superposition, the calculus inside modern automated provers.

So the accurate picture of a proof is:

rewrites           replace equals by equals — the only purely syntactic row
+ assume/discharge   temporarily pretend things       (for → and ¬)
+ fresh variables    let n be arbitrary               (for ∀)
+ witnesses          exhibit a specific x             (for ∃)
+ case splits        prove under A, then under ¬A     (for ∨)
+ induction          manufacture new hypotheses       (for ℕ, lists, trees)

Every row below the first creates structure — assumptions, variables, witnesses, branches — instead of rearranging existing syntax. And the insufficiency is not a design flaw of particular systems but a theorem: rewriting is complete for equations (Birkhoff), full logic is provably more expressive than equations, so no strengthening of pure rewriting can ever cover it. Which is reassuring in a way: if proving were just rewriting, mathematics would be mechanical, and considerably less fun.

The revenge: checking comes back to rewriting

Now the twist, and the actual answer to the title's question. Type theory's move is to make the proof itself a piece of data — a program — in which every structure-creating move becomes a programming construct:

Proof moveProgram construct
"suppose P…"lambda: λ p ↦ …
use an implication (modus ponens)function application
"let n be arbitrary" (∀)a function taking a value
exhibit a witness (∃)a pair: (witness, proof it works)
case splitpattern match
inductionrecursion

Read the table both ways, because both directions matter. Left to right: any proof — with all its assumptions, witnesses, and inductions — can be written down as a program, a finite object you can hand to a machine. The proof of "if P then (if Q then P)", which contained no rewriting at all, becomes the program λ p q ↦ p. The proof of n + 0 = n becomes a recursive function whose recursive call is the induction hypothesis — the "gift out of nowhere" is now just the argument the function receives.

Right to left is the Curry–Howard correspondence proper: the program's type is the proposition it proves, and a valid proof is exactly a well-typed program. Modus ponens and function application are not analogous; they are the same rule in two vocabularies.

This is why a program can check a proof. Checking is no longer "follow a chain of insight"; it is type checking — a local, mechanical procedure: check each part, check that the seams match. And here the rewriting intuition gets its revenge: a type checker constantly has to ask are these two types the same? — the proof claims to return evidence for succ(k) + 0 = succ(k) and actually returns evidence for succ(k + 0) = succ(k) — and it answers by rewriting: unfold definitions, reduce both sides, compare normal forms. So the engine at the bottom of the trusted kernel is precisely the match-and-reduce-on-syntax-trees machine from my original, wrong model of proving. It wasn't wrong; it was one level too high. Finding a proof needs search, witnesses, induction. Checking one needs a type checker, and the type checker's heart is a rewriter.

Proof by computation

Once checking is rewriting, an extreme regime becomes possible: some theorems need no clever moves at all, because the entire proof is the machine running. In Lean, theorem : 17 + 25 = 42 := rfl — the proof is the reflexivity constant, "true by computation"; the kernel reduces both sides to the same numeral and accepts. This is the Poincaré principle — a bare computation requires no proof steps — pushed as far as it goes. It scales: the Coq proof of the Four Color Theorem is mostly one gigantic, kernel-checked computation; decision procedures like ring and omega work by translating goals into a form where computation decides them. The technique is called proof by reflection: instead of writing a long rewrite sequence by hand, you write a program and let running it be the proof.

Axolotl is this regime, miniaturized to its essence. It has no numbers — its tests define them as Church numerals, a number being its own iterator — and no equality — defined à la Leibniz, two things being equal when every property of one is a property of the other. Then the test suite asks the kernel to certify that 2 + 2 = 4, with a proof consisting of the single constant refl. The only reason that certificate is accepted is that the checker's conversion rule genuinely evaluates plus 2 2 down to 4 while comparing two types. The arithmetic is performed by the type checker, during rewriting, as a side effect of an equality question. When certify(&statement, &proof) returns Ok(()), the whole argument of this post has just executed.

What has to hold

The edifice rests on one load-bearing property: well-typed constructions must actually deliver. A looping program inhabits any type, so if non-termination counted as proof, every proposition would be provable and the correspondence would collapse into triviality. This is why real kernels are pedantic — termination checking, positivity conditions, universe hierarchies forbidding Type : Type — each restriction guarding the same property. Axolotl skips almost all of it: it checks types in the lambda-Pi calculus and trusts you not to loop it. A demonstration of the principle, not a foundation.

But the demonstration is the point. The full picture, earned the long way around:

FINDING a proof:   search, witnesses, induction, creativity
                   — provably NOT rewriting; undecidable
                          │  produces a proof term (a program)
                          ▼
CHECKING a proof:  type checking, every equality question
                   settled by reduction
                   — IS rewriting; mechanical; fits in a small kernel

So: "proving is just rewriting" is false for finding, provably, and "checking a proof is mostly rewriting" is true by design — the central design idea of type-theoretic proof assistants, and the entire reason a few hundred lines of Rust can certify 2 + 2 = 4 without being taught arithmetic.

The axolotl, the animal, is a salamander that never grows up: it keeps its larval form its whole life, fully functional, never becoming the adult it could be. I can think of worse aspirations for a proof checker.
