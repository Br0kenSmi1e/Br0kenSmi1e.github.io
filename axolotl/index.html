Why a Program Can Check a Proof

November 2026

I recently built axolotl, a proof checker in about 600 lines of dependency-free Rust. But this post is not about the code. It's about the question the code answers — the question I actually wanted to understand by building it:

Why can a program check a proof at all?

A proof, after all, seems like the most human of artifacts: an argument, a chain of insight. Checking one feels like it should require understanding. And yet Lean, Coq, and Agda check proofs mechanically, and their trusted cores are small enough to audit by hand. What makes that possible? The answer is a sequence of three redefinitions, each one draining a little more of the mystery — until checking a proof has become arithmetic on syntax.

First redefinition: a proof is a construction

Ask what a proof is, and the everyday answer is a sequence of sentences, each following from the last. But there is an older and deeper answer, due to Brouwer and made precise by Heyting and Kolmogorov: a proof is a construction — a method.

Under this reading, a proof of "if A then B" is not a string of words about A and B. It is a method for turning any proof of A into a proof of B. A proof of "for every number n, P(n)" is a method that, handed any particular n, hands back a proof of P(n). A proof of "A and B" is a pair of proofs; a proof of "A or B" is a proof of one side, together with a note saying which.

This is a genuine change of ontology. Sentences are inert; you can only read them. Constructions are objects — you can write them down, compose them, and, crucially, inspect them piece by piece. And an object built by explicit rules from explicit parts can be checked by rule-following alone. Insight is required to find the construction. To verify it, none is.

Second redefinition: a proposition is a type

Here is the observation that makes the whole scheme go — the Curry–Howard correspondence. We already have a formalism whose entire purpose is to describe constructions and how they compose: the lambda calculus. And if you lay the proof-rules and the program-rules side by side, they are not merely similar. They are the same rules, written in two vocabularies:

Read the last three rows slowly, because they are the mechanism. Modus ponens — from A and A → B, conclude B — is the shape of applying a function to an argument: the argument has type A, the function turns A into B, the result has type B. Assuming a hypothesis and deriving a conclusion is the shape of a lambda: a construction awaiting an input. So a proof checker doesn't need to know what a proof means. It only needs to verify that each composition is type-correct — and type checking is a local, mechanical affair: check the parts, check that the seams match, done.

This is the point where "checking a proof" stops being a judgment and becomes a procedure.

Why it has to be Pi

The plain lambda calculus corresponds to a logic that can only rearrange bare propositions — A → B, and nothing about anything. Real mathematics quantifies over things: for every number n, for every point p. And that requires something that sounds exotic but is conceptually inevitable: a type must be allowed to mention a value.

Consider "n + 0 = n". This is not one proposition; it is a family of propositions, one per natural number. A proof of "for all n, n + 0 = n" must be a construction that takes n as input and produces a proof whose proposition — whose type — depends on the very n it was given. A function whose return type varies with its input. That is exactly the Pi type, the single constructor the lambda-Pi calculus adds to the plain one.

So the Pi is not a feature bolted on for expressiveness. It is the precise point where the calculus acquires a semantics: without it you have a logic about nothing; with it, a logic about things. Axolotl's entire term language is six constructors, and this is the one doing the heavy lifting — everything else is lambda calculus and bookkeeping.

Third redefinition: computation is not a proof step

If proofs are programs, then proofs compute — and this turns out to be the deepest practicality in the whole design. Ask: what should it take to prove that 2 + 2 = 4? Surely not a chain of lemmas. In a proof-as-program world, the proposition "2 + 2 = 4" is a type, and if you simply run the left side, it becomes "4 = 4". The reflexivity proof — the trivial construction that proves "t = t" for any t — therefore proves 2 + 2 = 4 as well, because after computation they are the same type.

The principle has a name: the Poincaré principle. A bare computation requires no proof; the machine just does it. Inside a checker, this is the rule of conversion (or definitional equality): two types that reduce to the same thing are the same type, full stop. It is what lets whole stretches of equational reasoning collapse into the checker silently evaluating both sides.

And it is why a kernel can certify arithmetic it was never taught. Axolotl has no numbers. Its tests define numbers as Church numerals — a number is its own iterator — and define equality à la Leibniz — two things are equal when every property of one is a property of the other. Neither is built in. Yet the checker certifies "2 + 2 = 4" and the transitivity of equality, because conversion makes the encodings compute, and computation is free. The type checker performs the arithmetic as a side effect of asking whether two types are equal.

What has to hold for this to work

The edifice rests on one load-bearing property: well-typed constructions must actually deliver. Every well-typed program must be safe to run — application never gets stuck, and, for the logic to be sound, every proof must terminate. A looping program inhabits any type; if non-termination were allowed as a proof, every proposition would be "provable" and the correspondence would collapse into triviality. This is why real kernels are picky in ways that feel pedantic — termination checking, positivity conditions, universe hierarchies that forbid Type : Type. Each restriction is there to protect the single property on which everything else stands.

Axolotl skips most of that. It checks types in the lambda-Pi calculus and nothing more: no termination checker, no inductive types, no universes beyond a bare hierarchy. So it is a demonstration of the principle, not a foundation you'd trust with the Kepler conjecture. But the demonstration is the point. The three redefinitions — proofs are constructions, propositions are types, computation is free — are not abstractions floating above the code. In axolotl each one has a home you can point to: the typing rules, the Pi constructor, the conversion check. About 250 lines of kernel, and the answer to "why can a program check a proof" fits inside them.

The axolotl, the animal, is a salamander that never grows up: it keeps its larval form its whole life, fully functional, never becoming the adult it could be. I can think of worse aspirations for a proof checker.
