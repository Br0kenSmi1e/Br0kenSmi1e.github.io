Axolotl

November 2026

I recently built axolotl, a proof checker in about 600 lines of dependency-free Rust. But this post is not about the code. It's about the question the code answers — the question I actually wanted to understand by building it:

Why can a program check a proof at all?

A proof, after all, seems like the most human of artifacts: an argument, a chain of insight. Checking one feels like it should require understanding. And yet Lean, Coq, and Agda check proofs mechanically, and their trusted cores are small enough to audit by hand. What makes that possible? This post is the answer, in the order I needed the ideas. Almost nothing in axolotl is invention; each piece exists because the previous idea demands it.

Logic is type checking

A proposition is a specification of what counts as evidence for it. A type is a specification of what counts as a member of it. These are the same notion — so every logical construct is a type:

So "is this a proof of P?" becomes "is this an element of type P?" — a mechanical question. Each shape of evidence has exactly one way to check it, every check is local, and there is no search. Example: "if A, then A" is proved by the identity function; checking that proof is checking one function body. This is the Curry–Howard correspondence: propositions are types, proofs are programs — and a proof checker is a type checker.

Why the lambda-Pi calculus?

So proofs are programs. But programs in which language? It turns out the logic itself dictates the answer — twice.

First, functions. Evidence for an implication is a method — something that takes evidence of A and produces evidence of B. So the language needs exactly two abilities: to build a method (introduce a hypothesis, use it in a body, discharge it — that is a lambda), and to use a method (feed it evidence — that is an application). Variables are the assumptions currently in play. A calculus with just variables, lambdas, and applications is the lambda calculus — not a choice among many, but the minimal machinery of "assume" and "therefore". Every construct is a proof move; there is nothing extra and nothing missing.

Then, dependency. Plain functions handle bare implications — A implies B, propositions about nothing. But mathematics quantifies over things: "for every number n, n + 0 = n" is not one proposition but a family, one per number. Evidence for it must be a function whose return type depends on the input value: feed it 3, get evidence of "3 + 0 = 3"; feed it 17, get evidence of "17 + 0 = 17". That single capability — types allowed to mention values — is the Pi type. It is the precise point where the logic acquires a subject matter.

That is the whole design. The lambda-Pi calculus is the smallest language in which every construct is a form of evidence: lambda is "assume", application is "use", Pi is "for all". Axolotl's entire term language is six constructors — variables, lambda, application, Pi, universes, annotations — and these two ideas are the reason those six suffice. What remains is engineering: how the machine actually evaluates, compares, and checks them. That is where the next idea lives.
