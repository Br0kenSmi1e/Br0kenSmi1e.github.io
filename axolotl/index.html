Axolotl

November 2026

I recently built axolotl, a proof checker in about 600 lines of dependency-free Rust. But this post is not about the code. It's about the question the code answers — the question I actually wanted to understand by building it:

Why can a program check a proof at all?

A proof, after all, seems like the most human of artifacts: an argument, a chain of insight. Checking one feels like it should require understanding. And yet Lean, Coq, and Agda check proofs mechanically, and their trusted cores are small enough to audit by hand. What makes that possible? This post is the answer, in the order I needed the ideas. Almost nothing in axolotl is invention; each piece exists because the previous idea demands it.

Logic is type checking

A proposition is a specification of what counts as evidence for it. A type is a specification of what counts as a member of it. These are the same notion — so every logical construct is a type:

LogicType
A ∧ B(A, B)
A → BA → B
∀x. P(x)(x : A) → P(x)
⊥∅
p proves Pp : P
P is trueP is inhabited

So "is this a proof of P?" becomes "is this an element of type P?" — a mechanical question. Each shape of evidence has exactly one way to check it, every check is local, and there is no search. Example: "if A, then A" is proved by the identity function; checking that proof is checking one function body. This is the Curry–Howard correspondence: propositions are types, proofs are programs — and a proof checker is a type checker.

Why the lambda-Pi calculus?

The table is a promise; now the language has to keep it. What machinery does it take to build and check evidence? The logic itself dictates the answer, twice.

Functions. Evidence for A → B is a method, so we need to build methods and use them. Write down the two rules for doing that, and something uncanny happens:

 x : A |- b : B                  f : A -> B    a : A
---------------------- (lambda)  ------------------- (application)
 |- fn(x){b} : A -> B                  f a : B

Read them aloud as logic: the first is "assume A, derive B, conclude A → B" — implication introduction. The second is modus ponens. The typing rules are the inference rules, in two vocabularies. Variables are the assumptions in play, and variables, lambdas, applications are the whole lambda calculus — not one choice among many, but the minimal machinery of assuming and concluding.

Dependency. But those two rules only build propositions about nothing: in A → B, the B is fixed before any input arrives. Real statements quantify over things — ∀n. n + 0 = n is a family of propositions, one per number — so evidence must be a function whose return type is computed from its argument:

proof : (n : Nat) -> (n + 0 = n)
                     ^^^^^^^^^^^ the return type mentions the input

That single capability — types mentioning values — is the Pi type, the point where the logic acquires a subject matter. And with that the design is done: lambda is "assume", application is "use", Pi is "for all". Axolotl's entire term language is six constructors, and these are why six suffice.

Why a checker, and its one guardrail

The correspondence says what a proof is — a program of the right type. But given a claim and a candidate, something still has to verify that the candidate actually has the claimed type. The checker is that verification.

Its rules are the logic's rules — the lambda and application rules above. But one extra rule answers to nothing but consistency. In this language types are values too — that is what dependency means — so we can ask: what is the type of a type? The tempting answer, Type : Type, is fatal: a type containing itself rebuilds Russell's paradox at the type level, and from it a proof of anything. So universes form a tower:

Nat  :  Type₀  :  Type₁  :  Type₂  :  Type₃  :  …

 each universe contains only what is smaller — never itself

And the tower pays a dividend: with it, and with no way to write general recursion, every well-typed term terminates, so the checker's "evaluate and compare" always finishes.

What lies outside the rules: axioms. Postulate anything and the kernel believes you. The checker guards the derivations, not the premises.

Axolotl, the artifact

axolotl is these ideas as running Rust — about 600 lines, zero dependencies — and two facts about it turn out to match the animal's two famous traits.

It is the theoretical minimum, and stays there. Six constructors, the rules above, and nothing else: no numbers, no equality, no recursion built in. Axolotls, the animals, are neotenic — they live their whole lives in larval form, fully functional, never becoming the adult they could be. The checker is neotenic too: a proof theory kept at its juvenile stage, deliberately never growing up.

It regrows whatever it lacks. The animal's other famous trait is regeneration: lose a limb, grow it back. The checker works the same way. It ships with no mathematics at all — and any missing piece, from numbers to equality to whole theories, is grown back by the user, as an explicit declaration, checked like everything else. Nothing is built in because nothing needs to be.
