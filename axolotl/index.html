Why a Program Can Check a Proof

November 2026

I recently built axolotl, a proof checker in about 600 lines of dependency-free Rust. But this post is not about the code. It's about the question the code answers — the question I actually wanted to understand by building it:

Why can a program check a proof at all?

The answer turns on one idea — propositions as types — and the idea is easier than its reputation. It took me a while to see it, because I kept asking the wrong question. This post asks the right one.

Flip the question

Don't ask "why are propositions types?" — that question has no satisfying answer. Instead, ask two easy questions separately, and watch the answers collide.

First: what is a type? Forget programming for a moment. A type is a specification that says what counts as a member of it. The type of natural numbers is the specification "things like zero, successor of zero, and so on." A function type is the specification "things you can call with an A to get back a B." That's all a type has ever been: a membership criterion. A type is defined by its elements.

Second: what is a proposition? Take the word "proof" seriously, and a proposition is a specification that says what counts as evidence for it. And every logical connective is literally defined this way:

  • "A and B" — evidence for it is evidence of A together with evidence of B. A pair.
  • "A implies B" — evidence for it is a method that converts any evidence of A into evidence of B. A function.
  • "there exists an x such that P(x)" — evidence for it is a specific x, plus evidence that P holds of it. A witness, with receipts.
  • "false" — evidence for it cannot exist. The empty specification.

Now put the two answers side by side: a type is a specification of members; a proposition is a specification of evidence. These are the same concept, named twice. The famous correspondence between logic and programming — Curry–Howard — is not a bridge built between two islands. It's the discovery that we had built one island and named it twice.

You might object: isn't a proposition just true or false? That's the classical view, and notice what it throws away. "There exists an even prime number" — the true/false view says true, full stop. The evidence view says: the number 2, together with a proof that 2 is prime. The evidence contains the witness, and you can take it out and use it. A proposition isn't a yes/no answer; it's a claim plus the receipts — which is exactly what a type with elements is. Truth and falsity then fall out for free:

true proposition   =  a type with at least one element
false proposition  =  an empty type
proof              =  an element

"2 = 4" is a perfectly legal type — it just happens to have no elements. Falsity isn't a red mark stamped on the proposition; it's the emptiness of its evidence class.

Checking a proof is checking membership

Here is where the machine enters. Once propositions are types, the question "is this a proof of the proposition?" becomes "is this an element of the type?" — and that second question has a mechanical answer.

Why mechanical? Because a proof, written as a program, announces its own structure. Every way of building evidence corresponds to exactly one rule of checking:

propositiontype

Read the last three rows slowly — they are not analogies. "Assume A, derive B, conclude A → B" and "write a function from A to B" are the same act described in two vocabularies. Modus ponens and function application are the same rule. So when the checker sees a function, it knows exactly what to verify: assume the hypothesis, check the body. When it sees a call, it checks that the argument's type matches the function's domain. Each shape of evidence dictates its own check, and every check is local: check the parts, check that the seams match, done.

The checker never searches. This is the great asymmetry at the heart of the whole enterprise: finding a proof is the hard, creative, undecidable part — nothing tells you which moves to try. Checking a proof, once one is handed to you, is a recursion over its structure with no choices in it. The human supplies the evidence; the machine verifies membership. A tiny, stupid, trustworthy machine.

Types that mention values

So far this only handles bare propositions — A implies B, with nothing the propositions are about. Real theorems mention things: "for every number n, n + 0 = n" is not one proposition but a family of them, one per number. Evidence for it must be a function whose return type depends on the input value — feed it 3, get evidence of "3 + 0 = 3"; feed it 17, get evidence of "17 + 0 = 17".

That construct — a function whose return type varies with its argument — is the Pi type, and it is the one essential addition to ordinary functions. It is not a feature bolted on for expressiveness. It is the precise point where types are allowed to mention values, and therefore where the logic acquires a subject matter. Without it: a logic about nothing. With it: a logic about things. Axolotl's entire term language is six constructors, and this is the one doing the work.

The type checker computes

Once types can contain values, a quiet consequence follows: to check whether two types are equal, the checker must evaluate the values inside them. And this turns out to be a gift, because it means computation inside a proof costs nothing.

Ask: what should it take to prove 2 + 2 = 4? Surely not a chain of lemmas. In this world the proposition "2 + 2 = 4" is a type, and if you simply run the left side, it becomes "4 = 4" — the same type. So the trivial proof of "everything equals itself" already proves 2 + 2 = 4: after the machine computes, there is nothing left to check. A bare calculation requires no proof steps; the machine just does it. This is why huge classes of theorems — polynomial identities, arithmetic facts, finite case analyses — are discharged in systems like Coq and Lean by what is literally one big evaluation.

Axolotl is this principle miniaturized. It has no built-in numbers — its tests define a number as its own iterator — and no built-in equality — two things count as equal when every property of one is a property of the other. Then a test asks the kernel to certify 2 + 2 = 4, and the proof offered is the single reflexivity constant. The only reason the certificate is accepted is that the checker, while comparing two types, genuinely evaluates "2 + 2" down to "4". The arithmetic is performed by the type checker, as a side effect of an equality question. When the test asserts the kernel says ok, the whole argument of this post has just run.

What has to hold

Everything rests on one load-bearing property: well-typed evidence must actually deliver. A program that loops forever could claim any type — so if non-termination counted as evidence, every proposition would be provable, and the whole correspondence would collapse. This is why real proof checkers are pedantic in ways that seem fussy: termination checks, restrictions on how types can refer to themselves, a strict hierarchy of universes. Each rule guards the same property.

Axolotl skips almost all of that. It checks evidence in the smallest calculus that has the Pi type, and trusts you not to loop it. A demonstration of the principle, not a foundation to build cathedrals on. But the demonstration was the point: the reason a program can check a proof fits in a few hundred lines, and the reason is not a trick. Propositions are specifications of evidence; types are specifications of members; they were the same thing all along — and checking that evidence matches its specification is something a machine has always been able to do.

The axolotl, the animal, is a salamander that never grows up: it keeps its larval form its whole life, fully functional, never becoming the adult it could be. I can think of worse aspirations for a proof checker.
